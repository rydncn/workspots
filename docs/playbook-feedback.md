# Playbook feedback from trial 2 (Workspots: Go, HTML, Postgres)

Where the playbook core at `f2fd445` was wrong, slow, missing something or assumed npm and TypeScript, and the reading taken. The playbook itself is not changed here.

## Reading and setup

1. **"Start here" is short and clear, but the core still points at npm-shaped artefacts.** The CI template, the hooks (`after-edit.mjs`, `before-stop.mjs`, `pre-push`) and `settings.json` all key off `package.json` scripts, Prettier and ESLint. For Go every one has to be rewritten rather than copied. Reading taken: keep the hook *behaviour* (format and vet after each edit, fast checks before stopping, plugin check, context budget) and reimplement each as a small Node script that runs `gofmt`, `go vet` and `go test` instead. `context-budget.mjs` and `check-plugins.mjs` are stack-neutral and copied as they are.
2. **`docs/new-project.md` is the only ordered checklist, and it isn't marked as core or not.** Steps 1 to 7 mix core items (CI, hooks, `CLAUDE.md`, settings, CODEOWNERS) with "add as it grows" ones (`docs/plans/`, `docs/handoff.md`, rule checks, the Claude review workflow). Reading taken: followed the README's core list and used `new-project.md` only for ordering.
3. **The context budget is unreachable in a cloud session.** The harness's system prompt and tool definitions here are roughly 80k tokens before the first message, so a 100k budget leaves about 20k of working room. Rule 17's figure is "a practitioner's threshold", but the hook measures total context, so in this environment it would warn almost at once. Reading taken: record peak context per session as the hook reports it, and treat the budget as "about 100k of *work* above the floor" (so roughly 180k reported) for deciding when to hand off. Noted so the comparison with trial 1 is honest.
4. **npm 11.10 or later is assumed; this environment had 10.9.9.** The `.npmrc` template needs it for `min-release-age`, and the CI template checks it, but `new-project.md` only says so in passing. Upgraded npm globally before the first install.
5. **The design template fits a Go project unchanged.** `DESIGN.md`, `ADR.md` and the given/when/then criteria needed no adaptation.
6. **`api.md` assumes JSON clients.** "Every error response is `application/problem+json`" leaves a browser user looking at raw JSON for a 404. Reading taken: the problem is still the canonical error; a request whose `Accept` prefers HTML gets the same fields rendered as a page. The template could say this in its browser section.
7. **`api.md` says failure messages mustn't reveal whether an account exists, but gives no pattern for sign-up.** A sign-up form that says "address taken" reveals it. Reading taken (AC7): the same page for both cases, with the difference only in the mail that would be sent.
8. **Rule 14 versus "show what would be sent in the development log".** A development mail outbox that prints the recipient is personal data in a log line. Reading taken: the dev outbox is its own plain stream, separate from the structured log, and the no-personal-data test runs against the structured log.

## As the work goes

9. **The design review by a person found four gaps the template's prompts didn't ask about:** login CSRF (tokens "tied to the session" when there is no session yet), session rotation at sign-in (in `api.md` but not surfaced as a criterion), a maximum password length so argon2id can't be used for denial of service, and how a local release rehearsal provides HTTPS when production mode insists on it. `api.md` could carry the first three as one-liners; `GATES.md`'s release row could mention the TLS proxy.
10. **A handoff file was needed after all.** The design session passed the context budget before slice 1 started (the harness floor is about 80k; see item 3), so `docs/handoff.md` was written to carry "design approved, start slice 1" into a fresh session. The task asked for a reason: the budget, not the size of the work.

11. **Hooks: the stack-neutral pair copied unchanged; the npm pair rewritten.** `context-budget.mjs` and `check-plugins.mjs` are stack-neutral. `after-edit.mjs` and `before-stop.mjs` are built around `package.json` scripts, Prettier and ESLint; the Go versions here are forty lines each (gofmt and `go vet` on the package of the edited file; gofmt, vet and `go test` before stopping). The `CHECKS` list idea carried over as is. The hooks' own test file (`hooks.test.mjs`) tests the npm behaviour, so it was not copied; the Go hooks were proven by planting a vet error and a failing test and watching each hook send the agent back.
12. **`settings.json`'s allow and ask lists are npm and Supabase shaped.** Trimmed to `go`, `gofmt`, `staticcheck`, `govulncheck`, the dev-db script, and `docker push`; the git and `gh` ask rules carry over unchanged.
13. **The CI template's job shape fits Go well.** Jobs, draft gating, concurrency, gitleaks and zizmor installs, and the agent-configuration step copied unchanged. Replaced: setup-node with setup-go, `npm run` steps with gofmt/vet/staticcheck, the npm audit with govulncheck, plus a Postgres service for the tests and an explicit "migrations on an empty database, twice" step. The lockfile and signature steps wait for `e2e/` in slice 2 rather than running on nothing (rule 9).
14. **Two gates could not be proven locally:** govulncheck (the vulnerability database is not reachable through this environment's proxy) and the whole-workflow run itself. Both are proven by CI's first run and a deliberately broken pull request.
15. **Rule 16's isolation advice is npm shaped** (`--randomize`, `sequence.shuffle`). Go's equivalents are `-shuffle=on`, `-count=1` and `t.Parallel()`; worth a line in the rule.

16. **The gitleaks proof advice needs one more word: entropy.** `new-project.md` and `GATES.md` say to plant "a `ghp_` token of the right length". A token of the right length made of one repeated character passes gitleaks' entropy check silently, and so did my first proof. Say "random characters", or give a command that generates one.
17. **The fresh-context review earned its place on slice 1 alone.** It found a real privilege gap (a default-privilege statement that stored nothing), a CI job that could pass on a failing test, and two criteria the tests claimed but didn't check, all before CI ran. The cost was one subagent run of about 140k tokens.
18. **Rule 9's "fail on nothing" needs a Go note on pipes.** `go test ./... | tee log` in a GitHub Actions `run:` step exits 0 on failure unless `shell: bash` (which adds `-o pipefail`) is set. The CI template's steps don't pipe, so it never meets this; a Go or shell adaptation does on its first `tee`.

19. **A planted secret on any branch turns every pull request's scan red.** `actions/checkout` with `fetch-depth: 0` fetches every branch, and `gitleaks git` scans every ref it finds, so the token planted on the throwaway branch failed the real slice's security job until that branch was deleted. The playbook's advice to "plant a token" should add: on a branch you can delete straight away, or in a scratch clone, and expect other open pull requests to go red meanwhile. (The cloud session's permission classifier also refused `git push --delete`, so the deletion needed a person.)

20. **The CODEOWNERS template's "make code owner review required" assumes a second person.** For a single developer whose agent commits under their own account, every pull request is their own, GitHub won't let them approve it, and the rule blocks every merge; it did here until it was switched off. The template and `new-project.md` step 3 should say: require it only when someone other than the author can review, otherwise rely on the PR's door section and the CI flag.

21. **"Every journey works without JavaScript" collides with axe.** axe-core is JavaScript, so a Playwright project with `javaScriptEnabled: false` (the natural way to prove AC29) hangs the axe run. The working pattern: take the page's HTML in whatever state it is, render it in a second JavaScript-enabled context at the same viewport with a `<base>` so the stylesheet loads, and run axe there. Worth a sentence in the accessibility row of `GATES.md`, since progressive-enhancement sites will hit it first.
22. **A strict CSP makes some planted breaks silent.** Planting an inline `style` to break a layout check does nothing when the CSP forbids inline styles; the gate "passed" and only a second look showed the break hadn't happened. Rule 15's "seen to fail for the right reason" applies to planted breaks too: check the break landed before trusting the red or the green.

23. **The CI template's npm version check fails on the Node the template itself selects.** `setup-node` with Node 22 (the current LTS) ships npm 10.9, so the template's "npm supply-chain settings take effect" step fails on its first run, which is the step working as designed but a trap for every new project. The template should add `npm install -g npm@11` (pinned) before the check, or say which Node major carries npm 11.10. Found by the e2e job's first full run here.

24. **`api.md`'s cookie rules meet Go's test tooling.** `Secure` cookies only round-trip through `httptest.NewTLSServer`, and `httptest.Server.Client()` returns one shared client, so "a browser per user" needs a client per browser or every user is the same person. Neither is in the template, and both cost an hour here. A Go note on the "How these are checked" section would save it.

25. **The whole-codebase review earned its place again, exactly as the README says.** After three slices it found twelve things three fresh-context reviews had passed, four of them must-fix, and four of those only visible with the slices read together: a cookie newly set on responses an earlier slice had made publicly cacheable, a rule the documents stated more strictly than the code, a route two documents promised that no slice had built, and a test harness about to collide with a new rate limit. Cost: one subagent run of about 205k tokens, the largest single review so far.

26. **A human review after both automated layers still found three real defects in slice 3.** An open redirect through a tab in the return path (browsers strip tabs; the check didn't), a check-then-count rate limiter that concurrent attempts walk through, and uncapped concurrent argon2id. Neither review brief named browser URL normalisation, concurrency or resource exhaustion, and neither reviewer went there unprompted. The playbook's review cadence could add a short list of question types the briefs must include for an auth change (what does the browser do to this value, what happens when twenty of these arrive at once, what does one of these cost), or route auth slices to the security audit earlier than "before the final review".

27. **Acceptance criteria written per behaviour miss what one actor can do to a shared result.** Thirty criteria, two automated review layers and a human review of slice 3 all passed a view that let one account outvote everyone on a spot's attributes; the human review of slice 4 caught it. The design template's prompt for unhappy paths ("empty, invalid, refused, offline, worst-case data") could add "one actor, many times" for anything aggregated or ranked.
